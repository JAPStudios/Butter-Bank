# Biscuits BFT consensus design (development branch)

## Protocol implemented in this branch

- Ed25519-signed proposals and prevote/precommit messages are domain-separated and bound to the chain ID, height, round, block hash, and validator-set hash.
- The proposer is selected deterministically from the active validator set. BFTChain rejects transactions with nonzero fee values, and the development configuration sets the block reward to zero. Consequently, this BFT chain does not collect transaction fees or mint block rewards. These settings do not establish a supply cap or issuance schedule; monetary issuance rules remain unspecified. Finalized-chain validation checks the coinbase recipient against the deterministic proposer for the block's height and commit round.
- Consensus round counters are unsigned 32-bit values (0 through 4,294,967,295); signed proposals, votes, round-change messages, certificates, and persisted signer state reject values outside that range.
- A commit certificate requires unique, valid precommit signatures representing strictly more than two-thirds of voting power.
- A prevote-certificate verifier checks unique, valid prevotes for one exact height, round, block hash, and validator set, with strictly more than two-thirds of voting power. The signer uses this shared verifier before persisting a lock.
- When a block commits through valid-round recovery, the finalized block stores the valid-round number and certificate. Chain validation rechecks that proof, and an offline signer may use it to catch up past a conflicting older lock (but still refuses a conflicting local precommit).
- Validator signing intents and locks are written to disk before signed messages are returned. A per-state-file OS process lock prevents two validator processes from using the same signer state simultaneously; existing state files must be regular files with mode 0600 and cannot be symlinks.
- The event-driven coordinator validates proposed blocks through a caller-supplied block validator, gathers votes, and finalizes only after a valid commit certificate.
- The HTTP transport relays signed proposals and votes, caps request bodies at 1 MB, limits concurrent handlers, and rate-limits each source address. Remote consensus listeners require mutual TLS: the server validates client certificates against a configured CA and an explicit SHA-256 certificate-fingerprint allowlist; outbound peer connections present a configured client certificate and validate the peer server certificate against the same trusted CA. Consensus message signatures are still independently checked.
- Admission certificates require signatures from strictly more than two-thirds of a configured issuer federation. Admitted validators receive equal voting power; no stake or token balance is used.

## Safety limits that are deliberate

The signer retains its lock when advancing on a >2/3 round-change certificate. A proposal for a different block must carry a signed, unique >2/3 prevote certificate for that exact block at a valid round strictly newer than the persisted lock and earlier than the proposal round. The proposal signature binds the valid-round metadata and certificate. The signer verifies and persists this authorization before signing a conflicting prevote, revalidates it after restart, and changes its lock only after a new-round >2/3 prevote certificate. Do not deploy this prototype as a production consensus network.

The implemented locked-round/valid-round transitions still need formal specification, adversarial testing, and independent protocol review before production use. Signed round-change messages, >2/3 round-change certificates, network relay, and inactivity-triggered timeout requests with bounded backoff are implemented. Validator-set transitions are committed to finalized blocks, verified against the validator set active before each transition, then activated at their declared heights; the consensus engine rotates signer state as the active set changes. Durable anti-rollback protection for signer state, authenticated operational peer management, and multi-process/multi-host fault tests remain outstanding.

## Stake-free admission and its trust assumption

A public network cannot be both permissionless and Sybil-resistant merely by removing mining and stake. This implementation therefore makes the admission trust assumption explicit: at least four independent credential issuers verify eligibility off-chain and sign a validator public key. At least four admitted validators are required, each with exactly one unit of voting power. Issuer keys and validator keys must be distinct. A four-validator set can tolerate one faulty validator while retaining a greater-than-two-thirds quorum. The chain stores no civil identity, only the key and issuer signatures. Issuers must enforce one active credential per eligible participant and coordinate revocation. The issuer federation and its governance must be chosen independently; code cannot prove that issuers are independent or prevent coercion, key sale, or issuer collusion.

The admission module is a mechanism, not a preselected list of real-world issuers. Before mainnet, publish issuer selection criteria, independence requirements, renewal and appeal procedures, revocation rules, privacy safeguards, and a public audit process.

## Node integration and remaining production blockers

The original node.py entry point remains proof-of-work for backward compatibility. The separate bft_node.py entry point uses BFTChain for certificate-validated block acceptance, persistent account state, transaction/mempool rules, peer synchronization, and a /propose API. Peer synchronization retrieves chain history through bounded pages of at most 100 blocks per response; peer response bodies are capped at 16 MiB, and the transaction client caps node responses at 4 MiB. BFTChain refuses proof-of-work mining and rejects blocks without a valid commit certificate. The test suite includes a four-node local network finality test and tests for conflicting longer forks.

This is an integrated development prototype, not a production-ready consensus protocol. Certificate-gated valid-round recovery now permits a locked validator to advance rounds without discarding its lock and to change its prevote only after validating a newer-round prevote certificate. This path still requires adversarial protocol review and expanded network-level fault testing. A stalled proposer or incomplete commit can still stall the chain. Validator-set transitions are committed to finalized blocks and activate at the declared height. Nodes derive the active set from verified history, rotate to a distinct signer-state file for each activation, and remain observers when their key is no longer admitted. The initial validator set and admission-issuer federation remain configuration inputs; issuer-federation changes are not chain-governed. Signer state is protected against accidental disclosure, concurrent-process races, accidental modification, and ordinary double-signing. A failed signer-state file or directory synchronization disables further signing in that process because the durable state is uncertain. A failed BFT chain-state file or directory synchronization also disables transaction admission, proposal validation, proposal construction, block finalization, and chain replacement in that process until restart and reconciliation. Local disk rollback after restart cannot be cryptographically prevented without a trusted monotonic store or equivalent operational control. Offline validators catch up from the active set's activation height; an embedded valid-round certificate may supersede an older lock, while a conflicting local precommit remains a hard stop.

The four-node test is a deterministic integration test, not a substitute for formal protocol review, independent security audit, network-partition testing, Byzantine fault injection, load testing, or a production incident/recovery exercise. Do not deploy with real funds or describe the system as production-secure until those workstreams and the issuer federation's governance decisions are complete.


## Running a development validator

1. Generate a key file with owner-only permissions:

   `PYTHONPATH=milkchain python -m keygen --output validator.key`

2. Each issuer independently signs the validator key. Put the federation's public keys in a JSON array file and run the issuer tool once per issuer:

   `PYTHONPATH=milkchain python -m admission_signer --issuer-key issuer.key --issuer-set issuers.json --chain-id milkchain-biscuits-devnet-1 --validator-public-key PUBLIC_KEY --issued-epoch 1 --expires-epoch 100`

   Collect more than two-thirds of the issuer signatures into that validator's admission certificate. Do not share issuer private keys or let the node operator make eligibility decisions for issuers.

3. Copy `milkchain/config.example.json` to a private `config.bft.json` file. Configure the issuer public keys, validator admission certificates, and current admission epoch in that copy. The committed example intentionally contains placeholders and is not a runnable network configuration. Use a unique BFT chain_id that is never reused by a proof-of-work network or another deployment; transaction signatures are scoped to chain_id.

4. For a remote consensus listener, configure a TLS server certificate/key, a trusted CA file, a client certificate/key, and the SHA-256 fingerprints of every permitted peer certificate in consensus_tls_peer_fingerprints. Bind consensus_host to the public interface and use HTTPS URLs in consensus_peers. Each node must trust the same issuing CA and allowlist the certificates of its peers; rotate certificates by distributing the new fingerprints before switching certificates. The TLS private key files must be owner-only (0600 on POSIX). A non-loopback listener without TLS is rejected. The node API is loopback-only; expose it externally only through an authenticated TLS reverse proxy. Keep validator.key and the signer state file backed up securely; never commit either file. The signer state must be a regular owner-only file (0600 on POSIX), symlinks are rejected, and an exclusive process lock prevents two node processes from signing with the same state. The node releases that lock on shutdown.

5. Start the BFT node:

   `PYTHONPATH=milkchain python milkchain/bft_node.py --config config.bft.json`

6. The selected proposer can request a proposal through the local node API using POST /propose with an empty JSON object. If the proposer is locked on a different block, include the exact candidate `block`, `valid_round`, and `valid_round_certificate` in the JSON request; the certificate must prove more than two-thirds prevoting power for that block at a round newer than the lock and earlier than the current round. Validators automatically prevote only after local block validation and signer authorization. A proposal may include a `validator_transition` certificate. Its activation height must be later than the block that commits it. The certificate must bind the chain ID, prior validator-set hash, next validator set, next-set hash, and signatures representing more than two-thirds of the prior set's voting power. Finality requires more than two-thirds of the active validator set's voting power.

This run mode is development software. Signed round-change certificates, automatic timeout requests, certificate-gated locked-round recovery, chain-committed validator-set transitions, historical set resolution, live signer rotation, and observer-only operation for removed validators are implemented. A validator transition is supplied as the `validator_transition` member of a proposal request; the selected proposer includes it in the finalized block. The new set becomes active at the certificate's declared height. Nodes derive the current set from the complete verified chain. A node whose key is removed stops signing; a node whose key is newly admitted opens a separate signer-state file for that activation. The node writes the finalized block before advancing signer height; offline signers can catch up by verifying committed certificates from the current set's activation height. Admission-issuer federation changes remain configuration-governed. Disk rollback protection still requires trusted monotonic storage or equivalent operational controls. Do not use real funds or deploy a public mainnet with this version.


## Round-change transport

Validators can issue Ed25519-signed round-change messages. Each message binds the chain, height, validator-set hash, and target round. The signer persists each message before returning it. The HTTP transport relays these messages at `/consensus/round-change`; a validator advances only after verifying unique messages representing strictly more than two-thirds of voting power. A locked validator retains its lock while advancing. A conflicting proposal requires a signed valid-round prevote certificate newer than the persisted lock; the signer persists that authorization before changing its prevote. Automatic inactivity-triggered round-change requests use bounded exponential backoff and preserve signer anti-equivocation rules. Timeout configuration rejects non-finite, non-positive, inverted, and non-representable values before starting the timer loop. Formal review and adversarial validation of valid-round recovery, validator-set changes, and production deployment hardening remain outstanding.
